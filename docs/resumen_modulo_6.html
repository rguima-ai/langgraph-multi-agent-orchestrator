Sistemas multi-agente
con LangGraph

Un sistema multi-agente divide un problema grande entre especialistas. Un Supervisor observa el progreso, decide quién trabaja después y termina solo cuando la respuesta cumple la calidad esperada.

TopologíasSupervisorEspecialistasEstado y reducersasyncioPydantic

01La idea central

Un solo agente con diez herramientas y un prompt enorme se confunde. Varios agentes chicos, cada uno con un objetivo claro, son más fáciles de controlar, probar y mejorar.

01

Dividir

Separar investigación, cálculo y redacción para que cada agente tenga una responsabilidad clara.

02

Coordinar

El Supervisor mira el estado y elige el próximo nodo. No hace el trabajo de los especialistas.

03

Validar

Cada resultado entra al estado solo después de cumplir un contrato de Pydantic.

04

Finalizar

El flujo llega a END cuando hay evidencia, análisis e informe suficientes, o cuando se agota el límite de pasos.

Analogía: una redacción periodística. El editor jefe (Supervisor) no escribe las notas: le pide datos al investigador, cuentas al analista y el texto final al redactor. Después de cada entrega revisa si alcanza.

02Topologías: cómo se conectan los agentes

La topología es el “organigrama” del sistema: quién puede pasarle trabajo a quién.

jerárquica

Jerarquía

Supervisor ↙ ↓ ↘ Inv. Anal. Sínt. ↘ ↓ ↙ Supervisor

Un nodo central decide el recorrido. Los especialistas nunca se llaman entre sí.

colaborativa

Colaboración

Inv. ⇄ Anal. ⇅ ╲ ⇅ Sínt. ⇄ Crít.

Los agentes se pasan la tarea entre ellos (handoffs) sin un jefe central.

secuencial

Secuencia

Inv. → Anal. → Sínt. → END

Un orden fijo, como una línea de montaje. No hay decisiones de ruteo.

Topología¿Quién decide el próximo paso?VentajaRiesgoCuándo conviene
JerarquíaEl Supervisor, según el estado.Control central, auditoría y una sola condición de parada.El Supervisor puede ser cuello de botella.Flujos con control de calidad y pasos que dependen de resultados.
ColaboraciónCada agente, al terminar.Flexibilidad y autonomía.Ciclos difíciles de predecir y depurar.Tareas abiertas y exploratorias.
SecuenciaNadie: el orden está fijo en el código.Muy simple y barata.No puede repetir ni saltear pasos.Procesos estables donde siempre se hace lo mismo.

La Pre-entrega 6 usa una topología jerárquica: es la que permite demostrar delegación dinámica, refinamiento (volver a pedir un trabajo) y una parada segura.

03El Patrón Supervisor

El Supervisor es un nodo que solo decide. Su salida es una decisión estructurada, no texto libre.

Supervisor→Especialista→Supervisor→… o END 
class SupervisorDecision(BaseModel):
    next_agent: Literal["researcher", "analyst", "synthesizer", "FINISH"]
    reason: str = Field(min_length=10)          # justificación breve y auditable
    quality_feedback: str                        # qué corregir si se pide refinamiento

decision = await model.with_structured_output(SupervisorDecision).ainvoke(mensajes)

Con Literal el modelo solo puede elegir entre cuatro valores: no existe la ruta "writer" ni "terminar". Además, el Supervisor aplica una rúbrica (¿hay al menos dos métricas con fuente?, ¿el cálculo declara su fórmula?, ¿el informe cita fuentes?) y puede reenviar el trabajo con quality_feedback.

¿Por qué todo vuelve al Supervisor? Porque después de cada aporte alguien tiene que comprobar si alcanza, si hay que refinar o si corresponde convocar al siguiente especialista. Ese “volver” es lo que convierte una secuencia en un sistema que se adapta.

04Especialización de agentes

Especializar es darle a cada agente un prompt, herramientas y contexto propios. Menos opciones significa menos errores.

AgentePromptHerramientasContexto que recibeNo debe…
InvestigadorBuscar evidencia verificable.search_market_dataPedido + feedback.Calcular porcentajes ni redactar.
AnalistaCalcular con datos ya investigados.calculate_percentage_changePedido + investigación + feedback.Buscar fuentes nuevas.
SíntesisRedactar el informe ejecutivo.Ninguna (salida estructurada).Pedido + investigación + análisis.Hacer nuevas búsquedas.

Con bind_tools([...], tool_choice=...) cada especialista ve solo su herramienta: el Investigador ni siquiera sabe que existe la calculadora. Es el principio de mínimo privilegio aplicado a agentes.

Sobre create_react_agent: en las versiones actuales de LangGraph está marcado como obsoleto. Por eso los especialistas son nodos async propios que usan bind_tools() o salida estructurada.

05Aristas condicionales

Una arista normal siempre va al mismo destino. Una arista condicional elige el destino leyendo el estado.

builder.add_edge(START, "supervisor")                # siempre empieza por el Supervisor
builder.add_conditional_edges(
    "supervisor",
    route_supervisor,                                 # función que lee el estado
    {"researcher": "researcher", "analyst": "analyst",
     "synthesizer": "synthesizer", "FINISH": END},
)
for especialista in ("researcher", "analyst", "synthesizer"):
    builder.add_edge(especialista, "supervisor")      # todos vuelven

La función de ruteo no interpreta el texto del usuario: solo lee la decisión ya validada.

def route_supervisor(state: AgentState) -> Route:
    if state.get("step_count", 0) >= state.get("max_steps", 8):
        return "FINISH"                               # freno de emergencia
    next_agent = state.get("next_agent", "FINISH")
    return next_agent if next_agent in ROUTES else "FINISH"   # ruta inexistente → terminar

06El estado compartido

El estado es la memoria de trabajo del grafo. Todos los nodos lo leen; ninguno lo modifica directamente.

class AgentState(MessagesState, total=False):   # MessagesState aporta `messages`
    request: str
    research_output: dict | None                  # parcela del Investigador
    analysis_output: dict | None                  # parcela del Analista
    final_report: dict | None                     # parcela de Síntesis
    next_agent: Route                             # parcela del Supervisor
    quality_feedback: str
    task_completed: bool
    step_count: int
    max_steps: int
    contributions: Annotated[list[dict], operator.add]   # acumulativa
    errors: Annotated[list[str], operator.add]           # acumulativa

Cada nodo es una función que recibe el estado y devuelve un diccionario con cambios. LangGraph combina ese diccionario con el estado anterior y guarda un checkpoint (en esta entrega, en SQLite con AsyncSqliteSaver).

07Aislamiento de escritura

Regla simple: cada campo tiene un único dueño.

CampoDueñoLos demás
research_outputInvestigadorSolo leen.
analysis_outputAnalistaSolo leen.
final_reportSíntesisSolo leen.
next_agent, step_count, quality_feedbackSupervisorSolo leen.
contributions, errors, messagesTodosAgregan elementos mediante reducers.

Así no puede pasar que el Analista “arregle” la investigación o que Síntesis cambie el porcentaje calculado. Si dos agentes escribieran el mismo campo, el último en terminar ganaría y el otro trabajo se perdería sin aviso.

08Reducers: cómo se combinan las actualizaciones

Un reducer es la regla que dice qué hacer con el valor nuevo y el viejo.

Sin reducer → reemplaza

step_count: antes 2, el nodo devuelve 3, queda 3.

Con operator.add → acumula

errors: antes ["A"], el nodo devuelve ["B"], queda ["A", "B"].

from typing import Annotated
import operator

errors: Annotated[list[str], operator.add]     # el nodo devuelve SOLO lo nuevo

# Dentro de un nodo:
return {"errors": [f"Analista: {exc}"]}          # ✓ actualización
state["errors"].append("...")                   # ✗ mutación directa: no se registra bien

messages usa el reducer add_messages (viene con MessagesState): agrega mensajes nuevos y reemplaza los que tengan el mismo id.

Ojo: si un nodo devuelve la lista completa en un campo con operator.add, los elementos se duplican. Siempre devolvé solo lo nuevo.

09Por qué usamos asyncio

Una llamada a un LLM o a una búsqueda pasa casi todo su tiempo esperando la red.

Síncrono

El programa queda detenido hasta recibir la respuesta. Nada más avanza.

Asíncrono

Con await, el event loop atiende otras tareas de entrada/salida mientras espera.

async def __call__(self, state: AgentState) -> dict:
    response = await self._model.ainvoke(mensajes)      # no bloquea el event loop
    raw = await search_market_data.ainvoke(args)

async for update in graph.astream(estado, config, stream_mode="updates"):
    print(update)                                       # cada nodo, mientras ocurre

En Jupyter y Colab se puede usar await directamente en una celda. En un script se usa asyncio.run(main()).

10Pydantic como contrato

El LLM puede devolver campos vacíos, un número fuera de rango o un cálculo que no cierra. Pydantic convierte esas expectativas en reglas ejecutables.

class AnalysisArtifact(BaseModel):
    start_value: float
    end_value: float
    result: float
    formula: str = Field(min_length=3)
    confidence: float = Field(ge=0.0, le=1.0)          # entre 0 y 1

    @model_validator(mode="after")
    def _result_matches_formula(self) -> Self:
        esperado = (self.end_value - self.start_value) / self.start_value * 100
        if abs(esperado - self.result) > 0.01:
            raise ValueError("El resultado no coincide con la fórmula.")
        return self

✓ Entra al estado

120 → 144, result = 20.0, confidence = 1.0

✗ Se rechaza

confidence = 1.7 o result = 25.0: el error queda en errors y el Supervisor decide qué hacer.

11Consistencia del estado

Que cada artefacto sea válido no alcanza: también tienen que ser coherentes entre sí.

Prerrequisitos

El Supervisor no delega en el Analista si no hay investigación, ni en Síntesis si falta el análisis. Tampoco puede elegir FINISH sin informe.

Invalidación aguas abajo

Si se rehace la investigación, el análisis y el informe anteriores se borran: estaban calculados con datos viejos.

Anclaje a la evidencia

El Analista solo puede usar valores que existan en la investigación, con la misma unidad. Síntesis debe citar al menos un source_id real.

Hilos separados

Cada ejecución usa su propio thread_id. Reusar uno continúa ese hilo y acumula sus listas en el checkpoint.

12Flujo de la Pre-entrega 6

Pedido: “Investigá el crecimiento del mercado de energía solar entre 2023 y 2024, calculá la variación porcentual y redactá una recomendación”.

START→Supervisor→Investigador→Supervisor→Analista→Supervisor→Síntesis→Supervisor→END
  1. Supervisor → researcher. No hay evidencia todavía.
  2. Investigador. Llama a la búsqueda simulada y obtiene 2023 = 120 y 2024 = 144 millones de USD, cada uno con su source_id.
  3. Supervisor → analyst. La investigación cumple la rúbrica.
  4. Analista. Calcula ((144 − 120) / 120) × 100 = 24 / 120 × 100 = 20% y guarda fórmula, valores, resultado e interpretación.
  5. Supervisor → synthesizer. Falta el informe.
  6. Síntesis. Produce título, resumen, evidencia con fuentes, recomendación y limitaciones.
  7. Supervisor → FINISH. El informe cumple la rúbrica: task_completed = true.

Si algo falla (timeout, rate limit, JSON inválido), el error se registra y el Supervisor aplica un ruteo defensivo. Si el problema persiste, max_steps corta la ejecución. La traza JSON guarda decisiones, contribuciones y artefactos; no guarda prompts ni razonamiento privado del modelo.

Datos simulados: la búsqueda usa una base local reproducible. Sirve para evaluar la arquitectura, no para tomar decisiones de inversión.

13Errores comunes

Supervisor infinito

Reenvía trabajo para siempre. Se evita con max_steps y un recursion_limit calculado a partir de él (2 supersteps por decisión).

Finalización prematura

Elegir FINISH sin informe. El Supervisor lo detecta y redirige al especialista que falta.

Supervisor trabajador

Si el Supervisor investiga o calcula, se pierde la separación de responsabilidades.

Estado mutable global

Usar .append() sobre listas compartidas. Los nodos deben devolver actualizaciones.

Output sin validar

Guardar en el estado lo que diga el LLM sin pasar por Pydantic.

Números inventados

Un cálculo correcto con datos que no vienen de la investigación. Hay que verificar el origen de cada valor.

Contexto excesivo

Pasarle todo el historial a cada especialista: más tokens y más confusión.

Error de red sin capturar

Timeouts y rate limits deben convertirse en errores registrados para permitir la recuperación.

14Glosario

AgenteUn LLM con un rol, un prompt y (opcionalmente) herramientas.
TopologíaLa forma en que se conectan los agentes: jerarquía, colaboración o secuencia.
SupervisorNodo central que decide el próximo paso y cuándo terminar.
NodoUna función del grafo que recibe el estado y devuelve cambios.
AristaLa conexión entre dos nodos.
Arista condicionalUna conexión cuyo destino depende del estado.
EstadoLa información compartida durante la ejecución.
Aislamiento de escrituraCada campo del estado tiene un único nodo dueño.
ReducerLa regla que combina una actualización con el valor anterior (reemplazar, acumular…).
SuperstepUn paso de ejecución del grafo; recursion_limit cuenta supersteps.
CheckpointerComponente que guarda el estado tras cada paso (aquí, SQLite).
thread_idIdentificador de una conversación persistida.
ToolUna función que el agente puede pedir ejecutar con argumentos estructurados.
ArtefactoLa salida validada y reutilizable de un especialista.
RúbricaLos criterios de calidad que usa el Supervisor para aceptar o pedir correcciones.
RefinamientoVolver a pedirle un trabajo a un especialista con feedback concreto.
TrazaRegistro de decisiones y contribuciones observables de una ejecución.
